# Правила совместной разработки

## 1. Структура веток

В репозитории используется следующая схема:

- **`main`** — стабильная версия.
- **`develop`** — общая ветка разработки.
- **`feature/*`** — разработка новых функций.
- **`fix/*`** — исправление ошибок.
- **`docs/*`** — изменение документации.

Новые рабочие ветки создаются от `develop`.

Изменения объединяются по схеме:

`feature/* → develop → main`

Прямые изменения в `main` и `develop` не допускаются. Для объединения используется Pull Request (PR).

## 2. Начало работы

Клонировать репозиторий (если он ещё не скачан):

```bash
git clone https://github.com/cherniakov/PaperTradingBot.git
cd PaperTradingBot
```

Использовать **Python 3.12.13** — версия зафиксирована в `.python-version`.

Перед созданием рабочей ветки убедиться, что текущие изменения сохранены:

```bash
git status
```

Перейти в `develop` и получить последние изменения:

```bash
git switch develop
git pull origin develop
```

Создать рабочую ветку:

```bash
git switch -c feature/название-функции
git push -u origin feature/название-функции
```

## 3. Сохранение изменений

После выполнения задачи:

```bash
git status
git add .
git commit -m "feat: описание изменений"
git push
```

Рекомендуемые префиксы коммитов:

- `feat:` — новая функция;
- `fix:` — исправление ошибки;
- `refactor:` — рефакторинг;
- `docs:` — документация;
- `test:` — тесты;
- `chore:` — технические изменения.

Не добавлять в Git `.venv`, пароли, токены, `.env` с секретами и другие локальные конфиденциальные файлы.

## 4. Обновление рабочей ветки

Перед обновлением сохранить текущие изменения в коммитах.

```bash
git fetch origin
git switch feature/название-функции
git merge origin/develop
```

Если возникли конфликты, разрешить их и проверить работоспособность кода.

## 5. Создание Pull Request

На GitHub открыть **Pull requests → New pull request**.

Для рабочей ветки выбрать:

- **base:** `develop`
- **compare:** `feature/название-функции`

В описании указать:

- Что изменено.
- Как проверена работоспособность.
- Есть ли известные ошибки или ограничения.

После создания PR дождаться проверки и одобрения.

## 6. Правила объединения

Для веток `develop` и `main` действуют правила защиты:

- Обязательный Pull Request.
- Минимум одно одобрение.
- Проверка Code Owner — `@cherniakov`.
- Повторная проверка после новых изменений в PR.
- Все обсуждения должны быть закрыты.
- Объединение только через **Squash and merge**.
- Запрещены принудительная перезапись истории и удаление защищённых веток.

Администратор репозитория может использовать предусмотренный правилами обход проверок через Pull Request при необходимости.

## 7. Выпуск изменений

После завершения разработки:

1. Рабочая ветка объединяется с `develop` через PR.
2. Изменения проверяются в `develop`.
3. Для выпуска создаётся отдельный PR `develop → main`.
4. После проверки изменения объединяются в `main`.

**Основное правило:** одна задача — одна рабочая ветка — один Pull Request.
